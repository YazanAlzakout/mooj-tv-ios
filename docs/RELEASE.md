# Release

**This is a new listing under `com.moojtv.player`, signed with Mooj's own key.**

Anything in this repository that says otherwise is inherited from the project
this was cloned from and is wrong here — see the superseded note in
`docs/DECISIONS.md`. The mistake is not recoverable: a package id, and the key
that first signs it, are both permanent. And nothing here will catch it for
you: every check in `tools/verify-brand.js` passes either way, because it
compares property *names*, not which key signed the artifact.

---

## Before you build

1. **Read a free `versionCode` from Play Console → App bundle explorer.** Never
   infer one from the repository. Git knows what was *built*, not what was
   *uploaded*: in the sibling project a code looked unused because no commit
   mentioned it, and Play refused the upload, because a build had reached a test
   track and left no trace. Put it in `VERSION_CODE_BASE` in `app.config.js` by
   hand — nothing increments it.

2. **Check the signing properties are present, and are Mooj's.** They live in
   `~/.gradle/gradle.properties`, outside the project, because
   `android/gradle.properties` is regenerated by prebuild:

   ```
   MOOJ_UPLOAD_STORE_FILE=D:/Projects/mooj-keys/mooj-upload.jks
   MOOJ_UPLOAD_STORE_PASSWORD=…
   MOOJ_UPLOAD_KEY_ALIAS=mooj-upload
   MOOJ_UPLOAD_KEY_PASSWORD=…
   ```

   The prefix is brand-specific and that is not cosmetic. This machine holds
   another app's upload properties in the same file, and
   `plugins/withReleaseSigning.js` activates on a property merely being
   present — a shared prefix signs Mooj with the other app's key, silently,
   with no error, until the Play upload, or never.

   With the properties **absent** the build falls back to the **debug** key
   rather than failing. That is why step 6 exists.

3. `node tools/verify-brand.js` — every check must pass.

## Building

**The Android release is built here, native and local, and never on EAS.** The
artifact that goes to Play is the one this machine produced. `eas.json`'s
`development` and `development-tv` profiles and the two `build:dev:*` scripts
exist for development clients only and must never be used for a release.

Apple platforms are the exception, and it is not a preference. There is no Mac
on this project, so `pod install` and Xcode cannot run here at all and EAS is
the only route to an iOS binary of any kind — which is why
`extra.eas.projectId` is back in `app.config.js` and `eas.json` carries an
`ios-simulator` profile, both added by hand on 2026-11-18. That profile builds
for the simulator only; nothing in this repository has ever produced a
submittable iOS build, and `docs/IOS_READINESS.md` records both what the four
Windows builds of that day did prove and what they cannot. AGENTS.md says the
same thing under "Where builds run"; if these two ever disagree, AGENTS.md is
the one agents read first and the one to fix.

Play needs an **AAB** (`bundleRelease`). An APK (`assembleRelease`) is for
sideloading onto a test device.

```
cd /d D:\Projects\mooj-tv
npm run prebuild
android\gradlew.bat -p android bundleRelease
```

### If you are building both the TV and the phone artifact

**Order does not save you; `--clean` does.** `expo prebuild` reuses an existing
`android/`, and `@react-native-tvos/config-tv`'s manifest edits are one-way — so
a phone prebuild on top of a TV tree leaves `android.software.leanback
required="true"` and the leanback launcher category sitting in the phone
manifest, and Play rejects it (the reasoning is in `app.config.js`).
`tools/verify-brand.js` cannot catch that: it only parses `uses-permission`.

All three prebuild scripts therefore pass `--clean`, and that is deliberate.
One consequence is expected and correct: `--clean` deletes `android/app/build`,
so `verify-brand.js` finds no merged manifest and falls back to the source one,
saying so. That is not a regression.

```
npm run prebuild:tv
android\gradlew.bat -p android bundleRelease      # the TV artifact
npm run prebuild
android\gradlew.bat -p android bundleRelease      # the phone artifact
```

On this machine a cold four-ABI parallel build has exhausted memory and crashed
the JVM. If that happens, build narrower:
`-PreactNativeArchitectures=arm64-v8a --no-parallel --max-workers=2`.

## After you build, before you upload

6. **Prove which key actually signed it.** Nothing in the repository can detect
   this, and it is the one mistake with no recovery.

   ```
   keytool -printcert -jarfile <aab>          # AABs carry a JAR signature
   apksigner verify --print-certs <apk>       # APKs are v2/v3-signed only
   ```

   Expected: `CN=Mooj TV, O=Mooj TV`, SHA-256
   `a629a385bec915e843fd2279dbd806ea42a1d04807900109ae6008715cc003f8`.

   Two other fingerprints can turn up there and both mean something went wrong:
   `c5ccca32…` is the other app's upload key, and `fac61745…` is the Android
   debug key — which is exactly what you get when a signing property is missing.

7. **Confirm the phone artifact is a phone artifact.** Read the AAB's
   `base/manifest/AndroidManifest.xml`, or
   `android/app/build/intermediates/merged_manifests/release/…`, and check there
   is no `android.software.leanback` and no `LEANBACK_LAUNCHER`.

8. **Test on hardware.** Nothing in this project is tested on a device
   automatically. The phone artifact goes on the owner's own phone; the TV
   artifact goes to the people named in `docs/TV_TEST_CHECKLIST.txt`.
